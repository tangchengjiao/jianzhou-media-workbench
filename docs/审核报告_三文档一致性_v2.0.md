# 三文档一致性审核报告

> 审核对象：PRD V2.0 ｜ 技术开发与实现方案 V2.0 ｜ 见舟工作台.html（原型 V2.0）
> 审核日期：2026-08-01
> 问题分级：**P0 阻塞**（不解决无法正确落地）｜**P1 重要**（逻辑不自洽或需求缺失）｜**P2 打磨**（体验与一致性问题）

---

## 一、P0 阻塞问题

### P0-1 技术方案 API 设计覆盖不全，开发无接口依据
- **现象**：技术方案 §14 仅定义了 7 组 API，但 PRD 要求的以下能力没有任何端点：系统设置的读写（§6.12 六个配置分区）、系统诊断与 Trace 查询、Usage Ledger / 预算查询、成长记录时间线与经验库、成长报告导出、创作者切换（PRD §5.4）、数据包详情/导出/删除影响计算、发布前判断锁定、T+N 快照查询。
- **影响**：开发阶段将自由发挥，接口与前端必然漂移，验收标准 §21 无法核对。
- **建议**：在技术方案 §14 补齐 5 组端点（settings / diagnostics / usage / growth / users），并为「预测锁定」「包切换」补端点。列入 v2.1 修订。

### P0-2 前端技术路线自相矛盾，必须二选一
- **现象**：技术方案 §1.2 要求「Vue 3 + TypeScript + Vite 构建」，同时又要求「首版不要求用户安装 Node.js」「MVP 可在 Windows 本地通过单一启动入口运行」。若严格按 Vite 工程，则用户机器要么装 Node 构建、要么开发者必须提交构建产物 dist——文档未说明这一点，也没有锁定方案。
- **影响**：开发路线不确定，直接影响 EXE 打包方式与可维护性。
- **建议**：明确二选一并写入文档（见「待确认决策 Q1」）：
  - 方案 A：Vue3 + Vite + TS 正式工程，仓库提交 dist 产物，运行零依赖（忠实原文档，工程化最完整）；
  - 方案 B：Vue 3 免构建（本地内置 vue.global 运行时）+ 模块化 JS，无构建步骤，`python app.py` 直接跑，打包最简单（偏离 §1.2，需修订文档）。

### P0-3 语音访谈在原型中完全没有"进行中"界面，P0 需求无交互依据
- **现象**：PRD §6.2 把语音访谈列为核心模块（访谈流程 9 步、状态机 12 态），技术方案 §4.3 定义了 CREATED→…→VERSION_CREATED 完整状态机；但原型只有一张"会话 #8 暂停"的静态卡片，没有：访谈进行中的对话界面、实时转写区、当前问题进度、追问展示、访谈结束后的字段候选确认流（原型把字段候选放在独立卡片，与访谈脱节）。
- **影响**：PRD P0 项「语音 IP 访谈」没有可开发的交互蓝本。
- **建议**：在原型补充访谈会话页（对话框 + 转写流 + 问题进度 + 结束后引导至字段确认），状态机与前端状态一一对应。

### P0-4 「无字幕时继续 ASR」在原型中默认勾选，违反显式授权原则
- **现象**：原型 `modal-plan` 中 `<input type="checkbox" checked>`。PRD §6.5 与技术方案 §6.2 均要求：无字幕时不得自动进入 ASR，**除非用户在本次任务中明确勾选**。默认勾选 = 默认授权，与原则相悖。
- **影响**：原则性违规，验收标准 12.3 不通过。
- **建议**：默认不勾选；勾选动作本身写入任务授权记录。

### P0-5 深/浅色主题需求不存在于任何文档
- **现象**：交付要求第四阶段提出双主题，但 PRD 与技术方案均无主题、外观、可访问性相关章节。
- **影响**：无文档依据，验收无标准。
- **建议**：PRD 增补「外观与主题」小节（双主题、一键切换、偏好持久化、跟随系统可选），技术方案增补设计令牌（design tokens）实现方式。列入 v2.1 修订。

## 二、P1 重要问题

### P1-1 内容库存状态集合三方不一致
- PRD §6.8：候选/已选题/提纲中/写作中/制作中/待发布/已发布/待复盘/已完成（9 态）；
- 技术方案 §8.1：CANDIDATE→…→RETRO_COMPLETED→ARCHIVED（10 态 + 3 可选态）；
- 原型看板：仅 7 列，缺「提纲中」「已完成」。
- **建议**：以技术方案状态机为准，原型补齐「提纲中」列，「已完成/归档」以筛选入口呈现（避免看板过宽）。三方写入同一张状态映射表。

### P1-2 品牌命名不统一
- PRD 标题「自媒体个人运营工作台」；原型文件与侧边栏「运营工作台」；文件名「见舟工作台」；示例用户「林小舟」。
- **建议**：统一品牌为「见舟 · 自媒体运营工作台」，简称「见舟工作台」；示例创作者保留「林小舟」作为演示数据包。

### P1-3 雷达信号卡字段与动作不完整
- PRD §6.4 信号卡字段 12 项，原型缺「链接」展示；
- PRD 卡片动作 7 项（加入观察/获取评论/提取文案/深度拆解/转为选题/忽略/不再推荐相似），原型各卡仅 2~4 个动作，「获取评论」全缺，「不再推荐相似」仅关键词卡有。
- **建议**：卡片动作区按信号类型给出可用子集，但至少提供「获取评论」入口；「链接」以图标形式呈现。

### P1-4 语音传输通道前后不一致
- 技术方案 §4.1 描述 MediaRecorder + WebSocket 流水线；§14.2 API 却只有 REST `POST /interviews/{id}/audio`。到底走 WS 还是 REST 分片上传没有定论。
- **建议**：首版采用 REST 分片上传 + 轮询/SSE 状态（实现简单、可审计、够用），WS 列为实时模式的可选升级，写入文档。

### P1-5 表达画像字段缺失
- PRD §6.2 列出 12 项（含禁用词、案例使用方式、自我称呼、用户称呼），原型仅展示 8 项。
- **建议**：按 12 项补齐，标注每项来源（语料统计 / 访谈 / 手动编辑）。

### P1-6 导航「默认只展开当前工作组」未实现
- PRD §4.2 明确要求，原型四个分组全部默认展开。
- **建议**：前端实现默认折叠、仅展开当前组，工作总台/资料中心/系统设置固定位置不变。

### P1-7 系统诊断与 Windows 交付目标矛盾
- 原型诊断页显示 FFmpeg 路径 `/usr/local/bin/ffmpeg`（类 Unix），产品定位是 Windows 本地优先。
- **建议**：诊断信息由后端真实探测生成，路径按运行平台显示。

### P1-8 创作工坊缺多平台版本管理
- PRD §6.7 稿件工作区含「平台版本」，技术方案 `CreationProject.platform_variants` 为列表；原型只有「当前平台版本：抖音」静态文字。
- **建议**：工作区加平台版本标签页（抖音口播 / 小红书图文），每版独立内容与修改记录。

### P1-9 多创作者切换只有 Toast，无流程
- PRD §5.4 定义切换 5 步（关闭包组合→激活新包→清空会话→保留系统配置→禁止跨用户检索），原型仅一个按钮。
- **建议**：实现切换确认弹层（展示将关闭/激活的包清单），切换后全局刷新上下文；演示环境提供第二个创作者数据包用于验证隔离。

### P1-10 时间硬编码、演示数据无标识
- 原型顶栏「5月20日 周一」硬编码，全部数据停在 2024 Q2；且无「演示数据」标识。若直接开发，容易把假数据当真实同步结果，触碰「无静默兜底」红线。
- **建议**：日期动态显示；Mock 必须做成**显式演示模式**（环境变量 DEMO_MODE，默认开启，UI 全局标注「演示数据」徽标），配置真实 API Key 后切换真实适配器——演示模式本身是用户可见、可关闭的，不属于静默兜底。

## 四、三方一致性良好、无需改动的部分

- 数据包 7 类模型：PRD §5.2 / 技术方案 §3 ActivePackageSet / 原型资料中心 7 张卡，完全一致；
- 执行计划确认卡 9 字段：PRD §6.5 / 技术方案 §6.1 ExecutionPlan / 原型 modal-plan，一致；
- 确认等级（无需/单次/二次）与原型弹层实现一致；
- 错误体系（Typed Error + Trace ID + 错误码分类）与原型错误弹层一致；
- 发布前判断不可覆盖：PRD §6.7 / 技术方案 §9.1 / 原型 lockPred 交互一致；
- 复盘链路（T+N 快照、规则建议人工确认）三方一致；
- 侧边栏信息架构（12 页面、分组、四字命名）三方一致。
