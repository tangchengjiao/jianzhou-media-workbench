# Phase 2.2：系统设置与模型 Provider 闭环

验收日期：2026-08-04

## 审查结论

改造前的系统设置只是“字段存储页”，没有形成配置闭环：EXE 默认强制进入演示模式，真实 Provider 不读取页面选择，自定义模型域名被硬编码允许列表拒绝，模型名称无法发现或验证，部分业务还把配置键名当成模型名传出。用户即使保存了地址、Key 和模型，也不能证明下一次任务真的会使用它们。

本轮将系统设置改为可验证的运行控制面。模式、Provider、鉴权和模型绑定均进入后端运行路径；测试操作明确区分“只保存”“读取模型列表”和“发起最小生成”，不再用保存成功代替服务可用。

## 已完成能力

1. “运行模式”独立成首个页签，Demo/Real 选择写入 SQLite、运行中即时生效，重启后恢复。首次使用新数据目录时才由 `JIANZHOU_DEMO` 决定初始值。
2. “大模型”支持 OpenAI Compatible 协议、自定义 API Base URL、Bearer API Key 或无鉴权本地服务。
3. 公网地址必须使用 HTTPS；回环和私有网络默认阻断。只有用户显式勾选“允许访问本机/私有网络模型服务”后才允许 HTTP，用于 Ollama、LM Studio 等可信服务。
4. 支持手填模型名称，也可调用 `GET {base}/models` 获取列表；模型列表不可用时不会阻断手填。
5. “测试快速模型”调用 `POST {base}/chat/completions` 发起最小生成，能区分未授权、余额/限流、网络不可达、非 JSON 和协议结构异常。
6. API Key 仍由当前 Windows 用户的 DPAPI 加密，SQLite 和设置响应只保存/返回配置状态。
7. TikHub 设置补齐 Base URL、平台、公开账号样本和真实测试入口，测试不再使用不存在业务含义的固定 `check_probe`。

## 协议依据与真实边界

模型发现按 OpenAI Models API 的 `GET /v1/models` 结构实现，最小生成按 Chat Completions API 的 `POST /v1/chat/completions` 结构实现：

- https://platform.openai.com/docs/api-reference/models/object?lang=curl
- https://platform.openai.com/docs/api-reference/chat?lang=ruby

自动化测试通过本机启动的 OpenAI Compatible HTTP 服务验证请求路径、请求体、无鉴权模式、模型列表响应和生成响应。这证明配置、网络请求和协议解析闭环真实存在，但不代表任意第三方中转或外部模型供应商已经通过生产验收；外部验收仍需用户自己的 URL、Key 和模型权限。

## 当前限制

- 本轮没有使用用户未提供的外部大模型 Key 产生计费请求，外部供应商状态仍为 `PARTIAL`。
- OpenAI Compatible 服务之间可能存在模型列表、参数和错误体差异；通过兼容协议不等于每家服务的所有扩展能力都可用。
- 运行模式切换不会删除已有演示记录，只影响之后发起的任务；数据清理/工作区切换应作为独立能力实现。
- 成本预算目前是配置和台账边界，尚未在所有 LLM 调用前形成统一的强制预算闸门。
