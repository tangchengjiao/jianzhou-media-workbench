# 自媒体个人运营工作台｜技术开发与实现方案 V2.0

> 文档状态：可用于技术评审、任务拆分与开发实施  
> 对应产品文档：PRD V2.0  
> 架构关键词：Local-first、模块适配、外部数据包、显式任务、可追溯、Fail-fast、无静默兜底

---

## 0. 技术设计目标

本系统不是将TikHub、ASR和大模型简单串联，而是构建一个可替换用户、可替换数据源、可替换模型、可追踪每次处理来源的个人创作者工作台。

技术实现必须满足：

1. 业务逻辑不依赖某个固定用户的数据；
2. 用户资料通过数据包挂载，不写死在提示词和代码中；
3. 账号监控与内容加工彻底解耦；
4. 下载、ASR、深度拆解和仿写必须由用户主动创建任务；
5. 所有AI写库结果必须通过结构校验；
6. 所有任务必须记录输入、输出、成本、模型、来源和错误；
7. 外部服务失败时不得伪造成功、不得静默切换服务商；
8. 工作总台作为控制面，具体页面对应独立领域服务；
9. 首版支持本地运行和轻量打包，不强依赖Redis、Kubernetes或大型中间件；
10. 未来可以扩展到服务端部署，但首版不为企业多租户过度设计。

# 2. 控制面与工作总台

## 2.1 Workbench Orchestrator

工作总台不是大模型随意调用所有能力的Agent，而是一个受约束的控制面。

职责：

- 查询全局状态；
- 汇总待办和重要信号；
- 解析用户命令；
- 调用白名单工具；
- 创建显式任务；
- 请求用户确认；
- 跳转到具体工作页；
- 汇总任务结果。

不负责：

- 直接执行未确认的付费动作；
- 直接修改正式IP档案；
- 自动采纳经验规则；
- 静默切换模型；
- 隐藏具体领域错误。

## 2.2 命令路由

命令路由优先使用规则和结构化意图，不使用一个超长Prompt处理所有动作。

```python
class CommandIntent(str, Enum):
    SHOW_STATUS = "show_status"
    START_PROFILE_INTERVIEW = "start_profile_interview"
    ADD_SIGNAL_TO_EXTRACTION = "add_signal_to_extraction"
    CREATE_TOPIC = "create_topic"
    ADJUST_PLAN = "adjust_plan"
    START_RETRO = "start_retro"
    OPEN_PAGE = "open_page"
```

LLM仅负责将自然语言解析为候选意图和参数。执行前由Pydantic校验，并由权限与确认策略判断是否允许。

## 2.3 监督者模式

复杂操作采用“总控 + 专项任务”模式：

- 总控保持会话上下文；
- IP访谈、内容拆解、文案生成等由独立任务执行；
- 专项任务返回结构化结果；
- 总控不直接共享所有工具权限；
- 专项任务失败时原样返回领域错误。

```python
class DataPackage(Base):
```

## 3.3 数据包版本策略

- IP档案、规则经验、运营周期使用不可变版本；
- 新版本创建后由用户选择是否激活；
- 原版本只读保留；
- 大型语料包允许增量添加来源；
- 删除来源前必须计算引用影响；
- 删除激活包必须先切换到其他包或明确停用相关功能。

## 3.4 Context Resolver

所有LLM任务执行前必须通过Context Resolver显式声明所需上下文。

```python
class ContextRequest(BaseModel):
    user_id: UUID
    task_type: str
    required_packages: list[str]
    optional_packages: list[str]
    max_tokens: int
    source_filters: dict
```

Context Resolver负责：

- 读取当前激活包；
- 验证用户隔离；
- 按任务选取必要资料；
- 返回引用ID；
- 记录哪些资料被送入模型；
- 不允许跨用户搜索。

# 4. IP语音访谈技术方案

## 4.1 推荐架构

首版推荐采用可审计的级联语音流水线：

```text
浏览器音频
→ VAD/分段
→ STT
→ 对话文本
→ LLM操盘手
→ 结构化追问或回答
→ TTS
→ 浏览器播放
```

原因：

- STT、LLM、TTS可独立替换；
- 每个阶段可记录和审计；
- 转写文本可以直接作为档案证据；
- 工具调用和结构化字段抽取更稳定；
- 更符合“数据包可替换、模型可替换”的架构。

首版不强制接入LiveKit。浏览器MediaRecorder + WebSocket即可完成一对一语音访谈。需要全双工、打断、弱网处理和多人实时场景时再引入LiveKit。

## 4.2 显式模式选择

系统提供：

- 文字访谈；
- 按键说话语音访谈；
- 实时语音访谈。

模式是用户明确选择，不得在语音失败后静默切换成文字并继续写档案。

## 4.3 InterviewSession状态机

```text
CREATED
→ DEVICE_CHECK
→ READY
→ RECORDING
→ TRANSCRIBING
→ THINKING
→ SPEAKING
→ PAUSED
→ SUMMARIZING
→ REVIEW_REQUIRED
→ CONFIRMED
→ VERSION_CREATED
```

失败状态：

- DEVICE_PERMISSION_DENIED；
- STT_FAILED；
- LLM_FAILED；
- TTS_FAILED；
- CONNECTION_LOST；
- STRUCTURE_VALIDATION_FAILED；
- USER_CANCELLED。

## 4.4 访谈数据模型

核心表：

- `interview_sessions`；
- `interview_turns`；
- `audio_segments`；
- `transcript_segments`；
- `profile_extraction_runs`；
- `profile_field_candidates`；
- `profile_versions`；
- `profile_field_sources`。

每个结构化字段必须记录证据：

```python
class ProfileFieldCandidate(BaseModel):
    field_path: str
    value: Any
    confidence: float
    evidence_turn_ids: list[UUID]
    inference_type: Literal["explicit", "summarized", "inferred"]
    user_confirmed: bool
```

`inferred` 类型不得自动进入正式档案。

## 4.5 语音模型适配器

```python
class STTProvider(Protocol):
    async def transcribe(self, audio: AudioInput, config: STTConfig) -> TranscriptResult: ...

class TTSProvider(Protocol):
    async def synthesize(self, text: str, config: TTSConfig) -> AudioResult: ...
```

适配器示例：

- LocalFunASRProvider；
- LocalFasterWhisperProvider；
- OpenAICompatibleSTTProvider；
- CustomHTTPSTTProvider；
- SystemTTSProvider；
- CloudTTSProvider。

适配器失败不得自动调用另一个适配器。

# 5. TikHub数据接入

## 5.1 适配器职责

TikHub只作为公开数据接入层之一，不直接渗透业务领域模型。

```python
class SocialDataProvider(Protocol):
    async def resolve_account(self, ref: AccountRef) -> CanonicalAccount: ...
    async def fetch_account_posts(self, account: CanonicalAccount, cursor: str | None) -> Page[CanonicalPost]: ...
    async def fetch_post_metrics(self, post: CanonicalPost) -> CanonicalMetrics: ...
    async def fetch_comments(self, post: CanonicalPost, request: CommentRequest) -> Page[CanonicalComment]: ...
    async def search_content(self, query: SearchQuery) -> Page[CanonicalSearchResult]: ...
    async def resolve_media(self, post: CanonicalPost) -> MediaReference: ...
    async def fetch_captions(self, post: CanonicalPost) -> CaptionResult: ...
```

## 5.2 Canonical Schema

所有平台返回统一结构：

```python
class CanonicalPost(BaseModel):
    provider: str
    platform: str
    external_id: str
    author_external_id: str
    url: str
    title: str | None
    description: str | None
    published_at: datetime | None
    duration_ms: int | None
    cover_urls: list[str]
    media_refs: list[MediaReference]
    raw_payload_hash: str
```

公开描述不能被标记为完整转写。

字段必须区分：

- `description_text`：平台描述；
- `caption_text`：平台原生字幕；
- `asr_transcript`：系统ASR结果；
- `clean_transcript`：模型或规则清洗结果。

## 5.3 自动同步范围

自动任务只做：

- 账号基础信息；
- 作品列表；
- 公开互动数据；
- 新作品发现；
- 已发布作品的数据快照；
- 低成本关键词搜索。

默认不做：

- 媒体下载；
- 字幕收费请求；
- ASR；
- 评论全量分页；
- 深度分析；
- Embedding。

## 5.4 同步策略

```text
Scheduler
→ 创建 SyncJob
→ TikHubAdapter
→ Canonicalize
→ Validate
→ Deduplicate
→ Transactional Write
→ Emit Domain Event
```

每次同步记录：

- provider_request_id；
- endpoint；
- 请求参数哈希；
- 返回状态；
- 是否收费；
- 缓存命中；
- 数据条数；
- 开始与结束时间。

# 6. 主动内容提取流水线

## 6.1 ExecutionPlan

用户点击“提取文案”后，系统先生成计划，不立即执行。

```python
class ExecutionPlan(BaseModel):
    task_type: str
    source_content_id: UUID
    steps: list[ExecutionStep]
    provider_calls: list[ProviderCallEstimate]
    estimated_cost: Decimal
    estimated_duration_seconds: int | None
    estimated_download_bytes: int | None
    cache_hits: list[str]
    outputs: list[str]
    retention_policy: str
    requires_confirmation: bool = True
```

用户确认后创建Job。

## 6.2 文本解析优先级

```text
1. 已存在且有效的本地缓存
2. 用户导入的正文
3. 平台原生正文
4. 平台原生字幕
5. 用户主动选择ASR
```

注意：这不是静默兜底。系统应显示当前可用来源，由用户选择执行路径。平台无字幕时不能自动进入ASR，除非用户已在本次任务中明确勾选“无字幕时继续转写”。

## 6.3 提取Job步骤

```text
RESOLVE_SOURCE
→ CHECK_CACHE
→ FETCH_NATIVE_TEXT
→ OPTIONAL_FETCH_CAPTION
→ OPTIONAL_DOWNLOAD_MEDIA
→ PROBE_MEDIA
→ EXTRACT_AUDIO
→ SPLIT_AUDIO
→ TRANSCRIBE_SEGMENTS
→ MERGE_TRANSCRIPT
→ VALIDATE_TRANSCRIPT
→ OPTIONAL_CLEAN_TRANSCRIPT
→ PERSIST_ASSETS
→ COMPLETE
```

## 6.4 资产不可覆盖原则

- 原始字幕不可覆盖；
- 原始ASR不可覆盖；
- 清洗文案使用新版本；
- 结构化稿件使用新版本；
- 任何修正都保存版本和操作者；
- 媒体删除不应删除已确认的转写，但要标记来源媒体已移除。

## 6.5 媒体缓存

目录建议：

```text
data/
  users/<user_id>/
    packages/<package_id>/
    sources/<source_content_id>/
      metadata.json
      media/
      captions/
      transcripts/
      comments/
      analyses/
```

缓存键：

```text
SHA256(provider + external_id + media_variant + source_version)
```

# 7. 内容拆解与创作编排

## 7.1 分离分析与生成

拆解任务与仿写任务必须分离：

- 拆解只回答原内容是什么；
- 个人化创作回答用户怎么表达；
- 不应在拆解结果中直接混入用户稿件；
- 每个结果独立保存和版本化。

## 7.2 Analysis Schema

```python
class ContentAnalysis(BaseModel):
    topic: str
    target_audience: list[str]
    user_problem: str
    hook: HookAnalysis
    structure: list[StructureNode]
    evidence: list[EvidenceItem]
    emotional_mechanisms: list[str]
    key_turns: list[str]
    cta: str | None
    comment_triggers: list[str]
    reusable_patterns: list[str]
    non_reusable_elements: list[str]
    source_citations: list[SourceCitation]
```

所有字段必须能引用原文区段。

## 7.3 创作上下文

创作任务明确加载：

- 当前IP资料包；
- 当前运营周期包；
- 用户确认的表达画像；
- 选中的来源内容；
- 选中的内容模式；
- 本人真实案例；
- 历史重复内容；
- 当前平台要求；
- 规则经验包。

不得默认把整个资料库全部发送给模型。

## 7.4 Creation Schema

```python
class CreationProject(BaseModel):
    topic: str
    goal: str
    target_audience: str
    references: list[UUID]
    differentiation_strategy: str
    personal_facts_used: list[UUID]
    outline: list[str]
    draft_id: UUID
    platform_variants: list[UUID]
    originality_report_id: UUID | None
    pre_publish_prediction_id: UUID | None
```

## 7.5 原创性检查

检查维度：

- 长句高度重复；
- 独有案例复用；
- 独有观点归属错误；
- 结构完全一致；
- 用户历史内容重复；
- 无本人事实和观点；
- 来源引用缺失。

原创性检查只提供风险，不做法律结论。

# 8. 内容计划与状态机

## 8.1 ContentProject状态机

```text
CANDIDATE
→ SELECTED
→ OUTLINING
→ DRAFTING
→ PRODUCING
→ READY_TO_PUBLISH
→ PUBLISHED
→ WAITING_RETRO
→ RETRO_COMPLETED
→ ARCHIVED
```

可选状态：

- PAUSED；
- CANCELLED；
- BLOCKED。

状态转换必须由明确事件驱动，不得由页面浏览自动改变。

## 8.2 产能计算

首版使用规则计算，不让LLM直接决定数量：

```text
可用时间
- 固定运营任务时间
- 已排内容预计时间
= 剩余产能
```

每种内容模板有预计时长区间。系统给出建议数量，用户确认。

## 8.3 发布登记

MVP不自动发布。用户填写：

- 发布平台；
- 发布链接；
- 实际发布时间；
- 最终标题；
- 最终稿件版本；
- 临时修改说明。

登记后创建数据快照计划。

# 9. 发布前判断与数据复盘

## 9.1 不可覆盖的预测记录

借鉴校准式内容实验：发布前判断创建后必须只读。

允许：

- 创建新版本；
- 添加补充说明；
- 发布后追加复盘。

禁止：

- 修改原预测数值；
- 删除原预测；
- 根据结果重写当初理由。

## 9.2 Prediction Schema

```python
class PrePublishPrediction(BaseModel):
    content_project_id: UUID
    goal: str
    expected_bucket: str
    confidence: float
    strengths: list[str]
    risks: list[str]
    hypothesis: str
    evidence_refs: list[UUID]
    user_judgement: str | None
    locked_at: datetime
```

首版使用相对表现区间，不使用虚假精确的播放量预测。

## 9.3 Snapshot策略

不同内容类型可配置：

- 短视频：T+1、T+3、T+7；
- 图文：T+1、T+7、T+30；
- 长文：T+3、T+7、T+30；
- 用户自定义。

## 9.4 规则更新

LLM只能产生 `RuleSuggestion`：

```python
class RuleSuggestion(BaseModel):
    action: Literal["create", "update", "deprecate", "observe"]
    rule_text: str
    evidence_publication_ids: list[UUID]
    confidence: float
    scope: RuleScope
    impact_summary: str
```

用户确认后才创建新规则包版本。

# 10. 外部导入系统

## 10.1 导入目标

导入系统必须与对标监控和TikHub解耦。用户可以单独导入：

- 自己账号历史数据；
- 平台后台数据；
- 对标样本；
- 历史脚本；
- 评论反馈；
- 内容表现表；
- 课程和资料；
- 已有IP档案。

## 10.2 Import Pipeline

```text
UPLOAD
→ INSPECT
→ SELECT_TARGET_PACKAGE
→ DETECT_SCHEMA
→ FIELD_MAPPING
→ PREVIEW
→ VALIDATE
→ DEDUPLICATE
→ BUILD_IMPORT_PLAN
→ USER_CONFIRM
→ TRANSACTIONAL_WRITE

```

## 10.3 字段映射模板

保存映射模板：

- 模板名称；
- 来源平台；
- 文件特征；

- 时间和数字格式；
- 缺失字段策略；
- 冲突策略。

- 只保存；
- 不自动分析；
- 不自动Embedding；
- 不自动写入正式IP档案；
- 不自动生成规则；
- 用户可勾选一批数据发起后续任务。

## 10.5 事务与回滚

- 每个导入批次单独事务；
- 允许“全部失败全部回滚”；
- 大文件分块时记录成功块和失败块；
- UI必须明确是完整成功、部分成功还是失败；
- 部分成功不能显示绿色“导入完成”而不说明失败行。

# 11. Job系统

## 11.1 为什么需要Job

以下任务耗时、收费或需要恢复：

- TikHub同步；
- 评论抓取；
- 媒体下载；
- ASR；
- 深度拆解；
- 多样本比较；
- IP化创作；
- 大文件导入；
- 数据复盘。

## 11.2 Job状态机

```text
DRAFT
→ WAITING_CONFIRMATION
→ QUEUED
→ RUNNING
→ SUCCEEDED

RUNNING → FAILED
RUNNING → CANCEL_REQUESTED → CANCELLED
FAILED → RETRY_REQUESTED → QUEUED
```

不存在自动变为成功的状态。

## 11.3 Job表核心字段


## 11.4 重试规则

“无兜底”不等于不能重试，但重试必须透明：

- 同一提供商、同一参数的网络瞬时错误可配置一次透明重试；
- 重试次数写入日志；
- 不允许自动切换提供商；
- 付费请求是否已经扣费必须记录；
- 超过透明重试后直接失败；
- 用户修复后可以手动重试。

# 12. Fail-fast与错误体系

## 12.1 核心原则

系统必须有完整错误处理，但不能用错误处理掩盖错误。

### 禁止

- `except Exception: return {"success": true}`；
- 返回空列表冒充真实无数据；
- 返回模板文案冒充模型结果；
- 自动切换模型；
- 自动降低分析级别；
- 缺失关键字段时继续写库；
- 文件下载失败后继续ASR；
- ASR失败后用description填充transcript字段。

## 12.2 Typed Error

```python
class AppError(Exception):
    code: str
    message: str
    stage: str
    retryable: bool
    provider: str | None
    details: dict
```

错误分类：

### 配置错误

- CONFIG_MISSING_API_KEY；
- CONFIG_INVALID_MODEL；
- CONFIG_FFMPEG_NOT_FOUND；
- CONFIG_STORAGE_NOT_WRITABLE。

### 数据源错误

- TIKHUB_UNAUTHORIZED；
- TIKHUB_INSUFFICIENT_BALANCE；
- TIKHUB_RATE_LIMITED；
- TIKHUB_ENDPOINT_NOT_FOUND；
- TIKHUB_PROVIDER_ERROR。

### 媒体错误

- MEDIA_URL_EXPIRED；
- MEDIA_DOWNLOAD_FAILED；
- MEDIA_FORMAT_UNSUPPORTED；
- AUDIO_EXTRACTION_FAILED。

### AI错误

- STT_PROVIDER_UNAVAILABLE；
- STT_TRANSCRIPTION_FAILED；
- LLM_PROVIDER_UNAVAILABLE；
- LLM_OUTPUT_INVALID；
- TTS_SYNTHESIS_FAILED；
- EMBEDDING_FAILED。

### 业务错误

- ACTIVE_PACKAGE_NOT_FOUND；
- PROFILE_NOT_CONFIRMED；
- SOURCE_TEXT_NOT_AVAILABLE；
- CONTENT_STATE_INVALID；
- PREDICTION_ALREADY_LOCKED；
- RULE_EVIDENCE_INSUFFICIENT。

## 12.3 API错误响应

```json
{
  "success": false,
  "error": {
    "code": "STT_TRANSCRIPTION_FAILED",
    "message": "第3个音频分片转写失败：模型进程已退出",
    "stage": "transcribe_segments",
    "provider": "local_faster_whisper",
    "retryable": true,
    "trace_id": "...",
    "details": {
      "segment_index": 3,
      "completed_segments": 2,
      "charged": false
    }
  }
}
```

## 12.4 顶层未知错误

允许顶层捕获未知异常以防进程崩溃，但只能：

- 写完整堆栈；
- 生成Trace ID；
- 返回 `UNEXPECTED_ERROR`；
- 不创建业务成功结果；
- 不隐藏原始日志。

这不是业务兜底，而是可观测性边界。

# 15. LLM任务规范

## 15.1 所有任务必须声明

- task_type；
- provider；
- model；
- prompt_version；
- schema_version；
- input_source_ids；
- active_package_ids；
- input_hash；
- token_usage；
- cost；
- output_hash；
- request_id。

## 15.2 结构化输出

所有写库型输出使用JSON Schema/Pydantic验证。

流程：

```text
模型输出
→ JSON解析
→ Schema校验
→ 业务规则校验
→ 来源引用校验
→ 写库
```

校验失败直接任务失败，禁止自动构造缺失字段。

## 15.3 提示词组织

不使用一个全局超长Prompt。提示词由以下部分组合：

- 固定任务协议；
- 当前用户IP摘要；
- 任务所需资料片段；
- 输出Schema；
- 任务特定约束；
- 来源引用格式。

## 15.4 模型路由

模型路由由用户配置或任务固定映射决定：

```text
快速分类 → fast_model
深度拆解 → analysis_model
文案创作 → writing_model
结构抽取 → structured_model
Embedding → embedding_model
```

模型不可用时直接报错。UI可提供“修改模型并重新执行”，但后端不自动替换。

# 16. 成本与缓存

## 16.1 Usage Ledger

每次外部调用记录：

- 用户；
- 任务；
- 提供商；
- 接口；
- 模型；
- 请求量；
- 费用；
- 是否缓存命中；
- 是否失败仍收费；
- 时间。

## 16.2 预算策略

- 80%预算：警告；
- 100%预算：阻止新的付费任务；
- 不影响本地浏览和历史数据；
- 用户可临时提高预算后继续；
- 不自动改用免费低质量模型。

## 16.3 缓存层

分别缓存：

- TikHub原始响应；
- 账号和作品快照；
- 媒体文件；
- 原生字幕；
- ASR结果；
- LLM分析结果；
- Embedding；
- TTS音频。

缓存命中必须校验输入哈希、模型版本和处理参数。

# 17. 安全与隐私

## 17.1 凭证

- API Key不得存入前端；
- Windows使用系统凭据管理器或加密存储；
- 本地配置文件只保存引用；
- 日志中脱敏；
- 导出包默认不包含密钥。

## 17.2 用户隔离

- 所有实体必须带owner_id；
- 文件目录按user_id隔离；
- Context Resolver强制用户过滤；
- 切换用户时清空会话缓存；
- 禁止使用全局无用户条件的语义检索。

## 17.3 删除

删除前展示：

- 数据量；
- 被引用的内容项目；
- 是否影响正式IP档案；
- 是否影响历史复盘；
- 是否只删除缓存或删除原始资产。

# 21. 技术验收标准

1. 用户切换只切换激活数据包，不修改代码和Prompt文件。
2. 所有高成本动作都必须先生成ExecutionPlan并确认。
3. 所有外部调用都有usage记录和request_id。
4. 所有LLM写库结果都经过Schema验证。
5. 所有内容资产都能追溯来源。
6. 原始转写、清洗文案和结构化脚本独立版本化。
7. 发布前判断不可覆盖。
8. 规则建议未经用户确认不得生效。
9. 任意失败都返回具体错误代码、阶段和Trace ID。
10. 不存在静默模型切换、空数据伪成功或模板兜底。
11. 工作总台能读取全局状态，但领域写操作仍由对应服务完成。
12. MVP可在Windows本地通过单一启动入口运行。

# 22. 关键技术决策摘要

1. 使用控制面协调各领域服务，不构建一个拥有无限权限的万能Agent。
2. 使用外部数据包实现用户可替换性和资料隔离。
3. 语音访谈首选STT-LLM-TTS级联，保证可替换和可审计。
4. TikHub只负责公开数据和媒体引用，不把描述字段冒充完整文案。
5. 自动监控与主动内容加工分开设计。
6. 所有昂贵动作先生成执行计划。
7. 原始资产不可覆盖，衍生资产版本化。
8. 用状态机和Job驱动长任务，不靠页面状态猜测。
9. Fail-fast代表显式失败，不代表不处理异常。
10. 不允许静默降级、伪成功和隐藏服务商切换。
